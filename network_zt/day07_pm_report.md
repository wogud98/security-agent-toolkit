## 6교시 · 내 이미지 만들기 (Dockerfile)

### 문제 6-1 · Dockerfile 두 줄을 써서 내 이미지 만들기

- (가) 내가 쓴 Dockerfile 두 줄을 붙여 넣어 주세요.
  - 쓸 내용: Dockerfile 두 줄(`FROM` 줄 · `COPY` 줄)
  - 답:
```bash
 => [1/2] FROM docker.io/library/nginx:1.28@sha256:146adea4768b83c607d0bdfa4188464e3da6e0a3ad4475db1d1d8f64f27c29c  1.6s
  => [2/2] COPY site-three/index.html /usr/share/nginx/html/index.html                                               0.5s
```

- (나) 🔍 `FROM` 과 `COPY` 가 각각 하는 일을 적어 주세요.
  - 쓸 내용: ① FROM 이 하는 일 ② COPY 가 하는 일
  - 답:
  *FROM nginx:1.28 은 새 이미지에 포함할 기존 이미지로 nginx:1.28 을 정합니다. 새 이미지에는 이 이미지의 내용이 모두 들어가고, 거기에 내 파일이 추가됩니다.*  
  *COPY site-three/index.html /usr/share/nginx/html/index.html 은 내 PC의 site-three/index.html 을 이미지 안의 nginx 가 응답하는 파일 자리로 복사해 넣습니다.*
  FROM : Dockerfile 첫째 줄을 처리한 단계입니다. nginx:1.28 기존 이미지를 확인했고, sha256: 뒤의 긴 숫자는 그 이미지의 고유 번호입니다.
  COPY :  내 파일이 이미지 안에 들어간 것입니다.

- (다) 🔍 5교시와 달리 `docker run` 에 `-v` 가 없는데도 내 화면이 나오는 이유는 무엇인가요?
  - 쓸 내용: ① 어제 파일이 컨테이너에 닿던 방법 ② 오늘 파일이 서버에 있는 위치와 시점
  - 답: 
```
내 파일이 docker build 때 이미지 안에 복사되어 이미 들어 있기 때문입니다. 5교시에서는 파일이 내 PC에 있고 -v 로 연결해야 컨테이너가 볼 수 있었지만, 이번에는 이미지 안에 파일이 들어 있어서 연결이 필요 없습니다.
```

- (라) 🔍 `docker build` 출력에서 `[2/2] COPY` 줄과 `naming to` 줄을 붙여 넣고, 각각 무엇을 알려 주는지 적어 주세요.
  - 쓸 내용: ① 두 줄 ② 각 줄이 알려 주는 것
  - 답:
```
[2/2] COPY … 줄은 Dockerfile 의 두 단계 중 둘째(COPY)가 실행되어 내 site-three/index.html 이 이미지 안에 들어갔다는 것을 알려 줍니다. 이 줄 앞에 CACHED 가 있으면 전에 같은 내용으로 만든 결과를 다시 쓴 것입니다.

naming to …my-nginx:1 줄은 만든 이미지에 my-nginx:1 이라는 이름이 붙어 build 가 성공했다는 것을 알려 줍니다. 이 줄이 없으면 docker run 에 쓸 이름이 없습니다.
```


## 7교시 · 이미지 버전 다루기 · 되돌리기 · 정리 · 올리기

### 문제 7-1 · 파일을 고쳐 보고, 이미지를 다시 만들어 반영하기

- (가) 파일을 고친 직후 새로 고침했을 때 화면에 무엇이 나왔나요?
  - 쓸 내용: 새로 고침했을 때 보인 화면의 큰 제목
  - 답: V1과 같은(수정 전) 화면이 보임, site-three

- (나) 🔍 파일을 고쳤는데도 화면이 바뀌지 않은 이유와, 바꾸려면 무엇을 해야 하는지 적어 주세요.
  - 쓸 내용: ① 바뀌지 않은 이유(서버가 보는 파일이 어디 있는지) ② 바꾸려면 할 일
  - 답: Dockerfile은 이미지를 만드는 명령어를 담은 파일이며, COPY 명령으로 원본 파일을 이미지 안에 복사하기 때문에 이후 원본 파일을 수정해도 기존 컨테이너 내부 파일은 바뀌지 않습니다. 따라서 기존 컨테이너를 종료·삭제하고 이미지를 다시 빌드한 뒤 새 컨테이너를 실행해야 합니다.

- (다) 🔍 5교시의 `-v` 방식과 6교시의 이미지에 넣는 방식은 파일을 고쳤을 때 반영되는 방법이 어떻게 다른가요?
  - 쓸 내용: ① -v 방식의 반영 방법 ② 이미지에 넣는 방식의 반영 방법
  - 답:
```
① -v 방식: 내 컴퓨터의 파일과 컨테이너 내부 경로를 연결하므로, 원본 파일을 수정하면 컨테이너를 다시 빌드하지 않아도 변경 사항이 반영된다.

② 이미지에 넣는 방식: 파일이 이미지에 복사되어 있으므로, 원본 파일을 수정해도 기존 컨테이너에는 반영되지 않는다. 이미지를 다시 빌드하고 새 컨테이너를 실행해야 한다.
```

### 문제 7-2 · 이전 버전으로 되돌리고 쓰지 않는 이미지 지우기

  - 쓸 내용: ① 에러 문구의 핵심 ② 지워지지 않은 이유 ③ 해결한 순서
  - 답: *읽는 법: container … is using its referenced image 는 「컨테이너 80ea… 가 이 이미지를 쓰고 있다」는 뜻이라 지워지지 않습니다. 컨테이너 ID 는 3번의 docker ps 에서 본 my-site 의 ID 와 같습니다.* 컨테이너를 먼저 지우고  rmi명령을 실행한다.
```bash
Error response from daemon: conflict: unable to delete my-nginx:1 (must be forced) - container 51c7f055b3a1 is using its referenced image a16e66346190
```
```GPT
① 컨테이너가 이미지를 사용 중이어서 삭제할 수 있다는 충돌 오류가 발생했다. ② my-site 컨테이너가 my-nginx:1 이미지를 사용하고 있기 때문이다. ③ 먼저 docker rm -f my-site로 컨테이너를 삭제한 다음 docker rmi my-nginx:1로 이미지를 삭제한다.

참고로 docker rm -f는 실행 중인 컨테이너도 강제로 삭제합니다. 실습에서 컨테이너를 중지한 뒤 삭제했다면 docker stop my-site → docker rm my-site 순서도 가능합니다.
```
